F1 — RBAC & Authentication
Role-Based Access Control · JWT · 3 Roles
✅ Complete Phase 1
ระบบ
  • Login ด้วย Email + Password
  • JWT Access Token (หมดอายุ 15 นาที) + jti ป้องกัน replay
  • JWT Refresh Token (7 วัน)
  • ยืนยัน email ก่อน login ได้
  • Rate limit: 5 login/15 นาที ต่อ IP
  • บล็อก user ที่ status = false
  • Logout → blocklist token ใน Redis
3 Roles
Roleสิทธิ์
ADMINจัดการทุกอย่าง ทั้ง user, VPS, config, payment
SUPPORTดู/จัดการ VPS, ดู user, อ่าน config (ไม่มีสิทธิ์ write critical)
USERสั่งซื้อ, จัดการ VPS ตัวเอง, ชำระเงิน

Login Flow
POST /api/auth/login  { email, password }
  │
  ├─[rate limit]─ เกิน 5 req/15min? ──→ 429
  │
  ▼
  Find user by email
  │
  ├─ ไม่พบ ──────────────────────────→ 401 Invalid email or password
  │
  ├─ status = false ─────────────────→ 403 Account disabled
  │
  ├─ verifyPassword() ผิด ───────────→ 401 Invalid email or password
  │
  ▼
  Sign Access Token + Refresh Token  (Promise.all parallel)
  │
  ▼
  Redis: SET rt:{userId}  TTL 7d  (overwrite single session)
  │
  ▼
  ตรวจ pending_policy_ids  (active policies ที่ยังไม่ยอมรับ)
  │
  ▼
  200  { access_token, refresh_token, user, pending_policy_ids }

  ⚠  pending_policy_ids ไม่ว่าง → frontend ต้อง redirect หน้า accept policy ก่อน

F5 — VPS Management
Proxmox VE Integration · IP Pool · Provisioning · Auto-Expiry
✅ Complete Phase 4–5
Provisioning Flow
Order PAID → temp_vps created → Proxmox clone template → cloud-init → start VM → vps record created → temp_vps deleted
  • Fire-and-forget async provisioning
  • Admin retry manual: POST /api/vps/provision/:orderId
  • Queue view: GET /api/vps/queue
IP Pool
  • 2 ประเภท: PUBLIC (direct access), PRIVATE (NAT)
  • เพิ่ม IP ทีละ 1 หรือ bulk range (max 256)
  • IP ซ้ำ → skip อัตโนมัติ
  • ตรวจ allocated ก่อน assign
Lifecycle
  • Soft delete (deleted_at) ไม่ hard delete
  • Auto expire ด้วย cron (7-day grace period)
  • Force delete ทันที (Admin only)

VPS Provisioning Flow (หลัง Payment สำเร็จ)
Transaction PAID  (TrueMoney / Slip auto) หรือ Admin approve (PromptPay)
  │
  ▼
  สร้าง temp_vps record  (mark ว่ามี order รอ provision)
  │
  ▼
  provision()  [fire-and-forget — server ตอบ response ทันที ไม่รอ]
  │
  ▼
  Proxmox: clone template VM  (vmid จาก package.os.vmid)
  │
  ▼
  cloud-init inject:  IP, gateway, subnet, root password, hostname, user
  │
  ▼
  Start VM  →  poll Proxmox task  (timeout 60s)
  │
  ▼
  Assign IP จาก ip_pools  (status=true, ยังไม่ถูก assign)
  │
  ├─ PRIVATE IP package ──→  natService.allocate()  →  สร้าง nat_allocation + system port rule
  │
  ▼
  สร้าง vps record  +  ip_assignments record
  │
  ▼
  ลบ temp_vps record  ✓ provision สำเร็จ

  ✗ ถ้าล้มเหลวที่ขั้นตอนใด:
    temp_vps ยังอยู่ → ดูที่ GET /api/vps/queue
    Admin retry → POST /api/vps/provision/:orderId

F12 — VM Reconfigure & Upgrade
Mode A: Package Switch · Mode B: Custom Resources · Pro-Rate Billing
✅ Complete Phase 9
Mode A — Package Switch
  • เปลี่ยน package โดยไม่ reprovision
  • Upgrade (ราคาสูงขึ้น) → คิดค่า pro-rate ของวันที่เหลือ
  • Downgrade (ราคาต่ำลง/เท่ากัน) → เปลี่ยน spec ฟรี
  • สูตร: ceil((price_delta × days_remaining) / period)
Mode B — Custom Resources
  • ระบุ cores, memory_gib, disk_gb ทีละหน่วย
  • ราคาจาก system_config: pricing.cpu_per_core ฯลฯ
  • เพิ่ม → คิดค่า pro-rate; ลด → ฟรี

Apply Flow
Amount > 0 → PENDING → ชำระเงิน → applyUpgrade()
Amount = 0 → Auto-approve ทันที → applyUpgrade()
  • Acquire Redis lock (idempotent)
  • Proxmox: updateVmResources + resizeDisk + rebootVm
  • Update vps.current_* + monthly_price
  • User ยกเลิก upgrade order ที่ยัง PENDING ได้ (mark upgrade log เป็น failed) — แต่ order ที่ PAID/applied แล้วยกเลิกไม่ได้ (CANNOT_CANCEL_UPGRADE)
Audit Trail
  • vps_upgrade_logs บันทึก before/after specs + amount_charged
  • applied_at null = pending/failed; filled เมื่อ Proxmox สำเร็จ
